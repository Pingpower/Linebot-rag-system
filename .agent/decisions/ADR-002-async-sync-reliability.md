# ADR-002: 向量同步背景任務的可靠性與錯誤捕獲

**狀態**: 已採納
**日期**: 2026-07-17
**決策者**: AI / 用戶

---

## 背景

使用者在後台修改或新增知識條目後，發現去 LINE 實機測試時「查不到資料」或「修改無效」。經排查發現，資料確實有寫入關聯式資料庫，但負責產生向量的背景腳本 `sync_embeddings.py` 在 `subprocess.run` 執行時發生了「靜默失敗 (Silent Failure)」。這導致高達 271 筆資料的 Embedding 欄位為空 (`None`)，使得 RAG 檢索管線在做相似度比對時完全找不到這些條目。

## 決策

在 `app.py` 中呼叫背景同步腳本時，必須強制捕獲標準錯誤輸出 (`stderr`)，並將其記錄到應用程式層級的 Logger 中，避免子進程崩潰卻無人知曉。

## 考慮的選項

### 選項 A: 同步執行 (Synchronous Execution)

- ✅ 優點：可以直接將錯誤拋給前端，使用者當下就知道更新失敗。
- ❌ 缺點：打 API 算 Embedding 需要時間（尤其大量更新時），這會導致使用者的網頁請求卡住直到 Timeout，體驗極差。

### 選項 B: 非同步背景腳本 + 嚴格日誌紀錄 (目前採納)

- ✅ 優點：使用者感受不到延遲，介面秒回。錯誤會透過 `subprocess.run(capture_output=True, text=True)` 完整捕獲，後續維護只需看 log 就能精準除錯。
- ❌ 缺點：使用者當下以為成功了，但如果真的失敗，依然會出現「修改無效」的現象。

## 理由

我們必須兼顧使用者體驗（不能卡頓）與系統的除錯能力。透過引入嚴格的 `capture_output` 加上 `logger.error`，我們能確保任何導致 RAG 失憶的錯誤都會被明顯記錄下來。這讓我們這次能迅速抓出並手動重新執行那 271 筆的補訓。

## 影響

### 正面影響

- 消除了靜默失敗的盲區。
- 保障了 LINE Bot RAG 系統的向量資料庫完整性。
